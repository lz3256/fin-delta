# FinDelta：4070 一周执行计划

## 本周验收标准

用 Qwen3-0.6B 完成固定真实财报算术子集上的 Base → LoRA SFT → DPO 比较；有训练日志、模型 adapter、预测原文、评测报告和失败案例。

**保底交付：Base + SFT 的完整闭环。DPO 在获得合格偏好对后执行。** DPO 无提升也是合法结果，不能反复查看 test 调参。单次训练只算探索性实验，不承诺一周达到岗位全部要求。

本周的研究问题：在相同模型、上下文和推理预算下，带证据来源的结构化 SFT 与经过审核的偏好训练，是否提高可验证算术正确率？

本周是 FinDelta 的第一阶段。真实多报告跨季度比较、语义引用验证、单位分类器、GRPO 和多卡扩展尚未实现，不能写成已完成成果。

## 必须由你作判断的部分

1. **金融标签审核。** chosen 的计算、分母、年份、单位是否正确？rejected 是否确实错误？若两个答案都合理，reject 该偏好对。不能只凭自动分数认定语义正确。
2. **失败归因。** 格式错误、证据数字不存在、错行/错期、错运算、单位错误分别记录；前两类可自动检测，后三类需人工分析。
3. **结果解释。** 比較同一 test cohort 的数值和置信区间；少量提升和单 seed 不足以声称稳健胜出。
4. **简历表述。** 使用实际模型规模、数据量、GPU 与结果；不把此项目描述成 既有机构工作 内部部署成果。

## 出现这些情况时怎样处理

- CUDA 不可用：把 runs/hardware.json 和 nvidia-smi 输出发回；不必先租卡。
- OOM：先在独立试跑目录试 0.6B QLoRA 配置；若需要缩短上下文，创建新 cohort，并重跑所有基线。不要静默裁掉证据或答案。
- 0.6B 大量输出非法 JSON：先查看样例，在 dev 上修改提示或增加 SFT 训练；修改后重跑 Base/SFT。不要只给微调模型更好的提示。
- SFT 无提升：检查训练 loss、目标格式、数据质量、是否过拟合；可做 100/500/1000 样本消融。不要把 test 当 dev。
- DPO 可用偏好少于约 50 对：本周报告 Base/SFT；继续扩充 train 采样或做明确标注的合成偏好试验。不要把无效/未审样本强行当“人类反馈”。
- DPO 比 SFT 差：报告该结果，检查偏好噪声、长度差异、学习率和数据量；这是研究结论，不是必须掩盖的失败。

## 一周之后

第 2 周：用 SEC 公开报告构造约 200–300 个经过审查的跨期问题，精确标注期间、单位和答案可得性；加入拒答训练及同格式负例。

第 3–4 周：做 SFT/DPO 消融与多 seed；在可验证任务上加入 GRPO，比较结果奖励和证据约束奖励。先测 4070 的 rollout 开销，再决定是否租 24/48GB 卡。

第 5–6 周：数据规模、模型规模和 GPU profiling；多卡只能在实际运行后写入简历。论文阅读与研究问题记录放入技术报告，不以框架清单替代结论。
